# Docker

Docker plays two separate roles in this project, both under `docker/`:

1. **Database for development** — `docker-compose.yml` brings up a SQL Server container, so
   development doesn't depend on a manual SQL Server install on the developer's machine.
2. **Packaging the API for production** — `Dockerfile.api` builds a backend image ready to run
   on any Linux server with Docker, including a production server.

Neither of them runs the frontend in a container — the Vite dev server (`npm run dev`) is only
for development; in production, `frontend/dist` (generated by `npm run build`) is a set of static
files, served by any ordinary web server (no container of its own needed).

## `docker-compose.yml` — SQL Server

```yaml
services:
  sqlserver:
    image: mcr.microsoft.com/mssql/server:2022-latest
    ports:
      - "1433:1433"
    environment:
      MSSQL_SA_PASSWORD: "${MSSQL_SA_PASSWORD:?set MSSQL_SA_PASSWORD in docker/.env}"
```

To use it:

```bash
cd docker
cp .env.example .env      # and edit MSSQL_SA_PASSWORD
docker compose up -d
```

This brings up a SQL Server reachable at `localhost:1433` with user `sa` and the password set in
`docker/.env` (gitignored file — never commit a real password). The named volume
`sqlserver_data` persists data between container restarts; `docker compose down -v` deletes that
volume and starts the database from scratch.

After bringing up the container, the backend's connection string (user-secrets, see
`docs/doc_backend.md`) should point to `Server=localhost,1433;...;Password=<same as .env>`.

## Docker and WSL

On Windows, Docker Desktop (with the WSL2 backend, the recommended option nowadays) actually runs
containers inside a Linux VM it manages itself (you may notice a distro named `docker-desktop`
when running `wsl -l -v` — that's this internal VM, not where you develop). Docker Desktop
exposes container ports (`1433:1433` in `docker-compose.yml`) to both Windows and any WSL distro
— so it doesn't matter whether the backend runs from Windows or from inside an Ubuntu WSL distro,
`localhost:1433` reaches the container either way.

This is quite different from a SQL Server installed natively on Windows: that one only accepts
"pure" loopback connections from Windows, which causes problems when the backend runs from inside
WSL (it only works by enabling WSL2's *mirrored networking*, a workaround setting). With SQL
Server in Docker, this problem doesn't exist.

Summing up the dependency relationship: **Docker Desktop needs WSL2** to work on Windows (it's
the virtualization mechanism it uses under the hood), but **the project itself doesn't depend on
WSL** — it depends on Docker. There's no WSL at all on the company's Linux server, just Docker
running directly on Linux.

## `Dockerfile.api` — packaging the backend

```dockerfile
FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build
...
RUN dotnet publish Inventory.Api/Inventory.Api.csproj -c Release -o /app/publish

FROM mcr.microsoft.com/dotnet/aspnet:10.0 AS runtime
...
EXPOSE 8080
ENTRYPOINT ["dotnet", "Inventory.Api.dll"]
```

Standard .NET multi-stage build: the first stage (`sdk`) compiles and publishes; the second
(`aspnet`, much smaller — just the runtime, no SDK) runs the final image. To build the image:

```bash
docker build -f docker/Dockerfile.api -t inventory-api .
```

(the trailing `.` matters — the build needs its context to be the repo root, because
`Dockerfile.api` copies `backend/` from there; running with the context inside `docker/` doesn't
work).

This image isn't used in day-to-day development yet — it exists ready for when the deploy to the
production server happens.

## Why this matters for portability

What's under `docker/` — the SQL Server image and the API image — is exactly what runs
identically on any operating system, Windows or Linux. That's why the most direct way to move
this project to a Linux production server is to reproduce these two containers there
(`docker compose up` + the `Dockerfile.api` image), without rewriting anything. Any part of the
project that depends on something installed manually outside a container (a SQL Server installed
natively on the host, for example) would **not** travel along with it — it would need to be
recreated manually on the server.
